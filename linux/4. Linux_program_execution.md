# Program Execution in Linux

When a user requests the execution of a program in a Linux operating system, a sequence of well-defined operations is carried out by the OS to create, load, and execute the process. This process involves both user-mode and kernel-mode activities and illustrates key OS principles such as process management, memory management, system calls, and CPU scheduling.

## 1. Process Creation

The initiation of program execution typically begins with a request made by an existing process (often a command-line shell) to create a new process. This is accomplished using the `fork()` system call.

- **fork():** The `fork()` system call creates a new process by duplicating the calling process. The new process is referred to as the child, and the original is the parent. Initially, the child is an exact copy of the parent, inheriting the code, data, and execution context. However, modern implementations use *copy-on-write* to defer physical duplication of memory pages until one of the processes modifies them.

- **exec():** The newly created process typically replaces its memory space with a new program using a system call from the `exec` family (e.g., `execve()`). This call discards the old address space and loads the binary of the requested program into the process’s memory, thereby transforming the child process into a new program.

## 2. Program Loading (Memory Image Construction)

Once the `exec()` system call is invoked, the kernel performs the following steps:

- **Binary Format Identification:** The kernel identifies the executable format (typically ELF in Linux systems) and invokes the appropriate binary handler (e.g., `load_elf_binary()`).

- **Segment Mapping:** The kernel maps the program’s code and data segments into the process’s address space. This includes:
  - `.text` section (executable code) as read-only and executable.
  - `.data` section (initialized data) as readable and writable.
  - `.bss` section (uninitialized data), allocated and zero-initialized.

- **Demand Paging:** Instead of loading the entire binary into memory immediately, Linux uses demand paging. Only the required pages are loaded as the program accesses them, utilizing the hardware’s page-fault mechanism.

- **Interpreter Handling (Dynamic Linking):** If the executable is dynamically linked, the ELF header contains an interpreter field (e.g., `PT_INTERP`) pointing to the dynamic linker (e.g., `/lib64/ld-linux-x86-64.so.2`). The kernel maps this interpreter and passes control to it. The interpreter then loads and links the shared libraries before transferring control to the program’s entry point.

## 3. Setting the Execution Context

Once the binary image is loaded:

- **Entry Point Determination:** The kernel sets the program counter (instruction pointer) to the entry point specified in the ELF header (field `e_entry`). This address corresponds to the `_start` symbol, typically provided by the C runtime.

- **Stack Initialization:** The kernel initializes the user-mode stack with arguments (`argc`, `argv`), environment variables, and auxiliary vectors, enabling the runtime to access startup parameters.

- **Transition to User Mode:** The kernel completes setup and transitions the process from kernel mode to user mode using a low-level instruction (e.g., `iret`, `sysret`, or `ret_from_fork`), beginning execution at the program’s entry point.

## 4. Program Execution (User-Mode Operation)

At this point, kernel put the process in ready Queue, the CPU begins executing instructions in user mode:

- **Execution Begins:** The `_start` routine (often written in assembly) is executed first. It prepares the environment for the main program by setting up the stack and invoking `main()`.

- **Instruction Execution:** The CPU fetches and executes instructions from the `.text` segment. Normal computation proceeds, involving arithmetic operations, memory access, control flow, etc., all within user-mode privileges.

## 5. System Call Interface

User-mode programs are restricted from directly accessing hardware or system resources. To request OS services, they must perform **system calls**.

- **Library Wrappers:** High-level functions such as `open()`, `read()`, and `write()` are provided by the C standard library (glibc). These act as wrappers that prepare system call arguments and invoke a CPU instruction (e.g., `syscall` on x86-64) to switch to kernel mode.

- **Register Convention:** The system call number and arguments are passed using specific CPU registers (e.g., `rax`, `rdi`, `rsi`, etc.). The `syscall` instruction triggers a trap into the kernel.

## 6. System Call Processing in Kernel Mode

Upon entering kernel mode, the system performs the following operations:

- **Trap Handling:** The CPU saves the current user-mode state and switches to the kernel stack. The kernel identifies the system call number and dispatches it to the corresponding system call handler.

- **Service Execution:** The kernel routine (e.g., `sys_read`) verifies the arguments, performs the requested operation (such as reading a file), and stores the result (or error code) in a designated register.

- **Concurrency Management:** If the system call involves blocking (e.g., waiting for I/O), the process may be placed in a wait queue, and the scheduler may select another process to run. Upon completion, the process is rescheduled.

## 7. Return to User Mode

After completing the system call:

- **Context Restoration:** The kernel restores the user-mode registers and execution context.

- **Result Delivery:** The system call return value is placed in a register (e.g., `rax`), and control returns to the user-mode program, which resumes execution at the instruction following the system call.

## 8. Process Termination

When the process completes execution (either by returning from `main()` or calling `exit()`), the following occurs:

- **User-Space Cleanup:** The C runtime performs cleanup actions (e.g., flushing buffers, calling `atexit()` handlers) and invokes the `exit()` system call.

- **Kernel Cleanup:** Upon entering kernel mode, the kernel:
  - Closes open file descriptors.
  - Releases allocated memory and resources.
  - Removes the process’s entry from kernel data structures (e.g., process table).

- **Exit Status:** The process’s termination status is stored until the parent process retrieves it using `wait()` or `waitpid()`. Until then, the process remains in a "zombie" state.

- **Reaping the Process:** Once the exit status is collected, the OS deallocates all remaining resources associated with the process.

---

This sequence illustrates the full lifecycle of a process in a Linux system, from creation through execution to termination. It demonstrates key OS mechanisms including **process creation**, **program loading**, **memory mapping**, **user-kernel transitions**, **system call handling**, and **resource management**—all essential concepts in modern operating systems.
